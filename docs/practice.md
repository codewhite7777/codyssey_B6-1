## 확인 문제

### 0단계 · 책 정보도 테이블로 나눈다면?

**문제**: rental에 `book_title`을 직접 적고 있을 때, 테이블을 나누려면 무엇을 만들고 rental의 어떤 칸을 바꿔야 하나?

**내 답**: 책 이름을 새로 나누고 멤버 아이디를 갖고 있으면 되나?

**결과**: 반만 맞음. book 테이블을 새로 만드는 건 맞지만, `member_id`는 book이 아니라 **rental에 그대로** 두고 rental에 `book_id`를 추가한다.
book에 `member_id`를 넣으면 책 한 권당 회원 칸이 하나뿐이라 여러 사람이 빌린 기록을 적을 수 없다.

### 2단계 · 카테고리 추가

**문제**: 책을 소설, 만화, 과학으로 분류하려면 어떤 테이블을 만들고 FK는 어디에 넣나?

**내 답**: 카테고리 테이블을 만들고, 책이 카테고리의 PK를 FK로 참조한다.

**결과**: ✅ 카테고리 1개에 책 여러 권(1:N)이므로 FK는 N 쪽인 book에 둔다.

### 3단계 · 제약조건 고르기

**문제**: member의 `name`, `email`, `phone`에 NOT NULL과 UNIQUE 중 무엇을 걸까?

| 컬럼 | 내 답 | 피드백 |
|---|---|---|
| name | NOT NULL | ✅ 동명이인이 있으니 UNIQUE는 안 건다 |
| email | NOT NULL | NOT NULL + UNIQUE 추천. 이메일은 회원을 구분하는 값이라 중복을 막는 게 자연스럽다 |
| phone | UNIQUE | 가능. 다만 가족이 번호를 같이 쓰면 막히므로 아무것도 안 거는 경우도 많다 |

나는 "같은 사람이 이메일로 두 번 가입할 수 있다"고 생각했는데, 서비스가 그걸 허용하면 UNIQUE를 안 거는 게 맞다. 제약조건은 서비스 규칙을 옮기는 것.

### 4단계 · INSERT 순서 (1)

**문제**: DB가 **완전히 비어 있을 때** 아래를 순서대로 실행하면 어디서 에러가 나나? (FK 켜짐)

```sql
INSERT INTO rental (id, member_id, book_id, rented_at) VALUES (1, 1, 1, '2026-10-01');
INSERT INTO member (id, name, email) VALUES (1, '김철수', 'kim@a.com');
INSERT INTO book (id, title, category_id) VALUES (1, '해리포터', 1);
```

**내 답**: 처음엔 "DB가 비어 있다"는 전제가 문제에 없어서 무엇을 묻는지 이해하지 못했다.

**결과**

| 줄 | 결과 | 이유 |
|---|---|---|
| rental | ❌ | 1번 회원, 1번 책이 아직 없음 |
| member | ✅ | 가리키는 부모가 없음 |
| book | ❌ | 1번 카테고리가 아직 없음 |

### 4단계 · INSERT 순서 (2)

**전제**: FK 켜짐. category에 1번 소설, 2번 만화. member에 1번 김철수. book, rental은 비어 있음.

| 순서 | SQL | 내 답 | 실제 | 채점 | 이유 |
|---|---|---|---|---|---|
| ① | `INSERT INTO book ... VALUES (1, '원피스', 2);` | 성공 | 성공 | ✅ | 2번 카테고리 있음 |
| ② | `INSERT INTO book ... VALUES (2, '코스모스', 3);` | 에러 | 에러 | ✅ | 3번 카테고리 없음 → **저장 안 됨** |
| ③ | `INSERT INTO rental ... VALUES (1, 1, 1, '2026-10-02');` | 성공 | 성공 | ✅ | 1번 회원, 1번 책 있음 |
| ④ | `INSERT INTO rental ... VALUES (2, 1, 2, '2026-10-03');` | 성공 | **에러** | ❌ | 2번 책은 ②에서 실패해서 **존재하지 않음** |

**배운 점**: 에러 난 INSERT는 저장되지 않아서, 그걸 가리키는 뒷줄도 연달아 실패한다. 에러가 여러 개면 맨 위부터 고친다.

### 5-1단계 · 기본 조회

**문제**: 가격이 10000원 미만인 책을 싼 순서대로 2권만 보여주는 SQL은?

**내 답**

```sql
SELECT title FROM book WHERE price < 10000 ORDER BY price ASC LIMIT 2;
```

**결과**: ✅ 원피스(5000), 슬램덩크(6000).

### 5-2단계 · INNER JOIN

| 문제 | 내 답 | 결과 |
|---|---|---|
| rental에 `id 4, member_id 3`이 추가되면 JOIN 결과에 붙는 이름은? | 박민수 | ✅ |
| rental에 `id 5, member_id 2`가 추가되면 생기는 줄은? | 5, 2, 2, 이영희 | ✅ |
| `SELECT book.title, rental.id FROM rental JOIN member ON rental.book_id = book.id;`는 실행될까? | 안 됨. member를 조인하면 book.title이 없으니까 | ✅ book을 꺼내지 않았음. `JOIN book`으로 고친다 |

그림 문제 2개(rental + book, book + category)는 대화 중 위젯으로 직접 풀었다. 문제와 정답만 남긴다.

| 문제 | 정답 |
|---|---|
| rental(book_id: 3, 1, 3, 2) + book(1 해리포터, 2 어린왕자, 3 원피스, 4 코스모스) 결과 | 원피스, 해리포터, 원피스, 어린왕자. 코스모스는 짝이 없어 빠짐 |
| book(category_id: 1, 1, 2, 2) + category(1 소설, 2 만화, 3 과학) 결과 | 소설, 소설, 만화, 만화 (4줄). 과학은 짝이 없어 빠짐 |

### 5-2단계 · LEFT JOIN

**문제**: 왼쪽과 오른쪽을 바꿔서 쓰면?

```sql
SELECT category.name, book.title
FROM book
LEFT JOIN category ON book.category_id = category.id;
```

| 문제 | 내 답 | 결과 |
|---|---|---|
| 전부 남는 왼쪽 표는? | 책의 타이틀 | 거의 맞음. title 칸이 아니라 **book 표 전체(모든 줄)** |
| 결과 표 | 소설 해리포터, 소설 어린왕자, 만화 원피스, 만화 슬램덩크, **과학 NULL** | 위 4줄 ✅, 과학 줄 ❌ |
| 과학이 나올까? | 나옴, LEFT JOIN이라서 | ❌ 과학은 **오른쪽** 표에 있어서 버려짐 |

**배운 점**: LEFT JOIN은 "짝 없는 줄은 다 남긴다"가 아니라 **"왼쪽(FROM) 표의 짝 없는 줄만 남긴다"**. 살리고 싶은 표를 FROM에 둬야 한다.

**문제**: "대여 기록이 없는 회원도 포함해서" 회원 이름과 대여 번호를 보려면 빈칸은?

```sql
SELECT member.name, rental.id
FROM ______
LEFT JOIN ______ ON rental.member_id = member.id;
```

**내 답**: member, rental → ✅

### 5-3단계 · GROUP BY

처음 GROUP BY를 COUNT, SUM, AVG와 함께 한 번에 배웠을 때는 이해하지 못했다. **COUNT 하나만, 카드 더미 그림으로** 다시 배우고 이해했다.

**문제**: rental(member_id: 1, 1, 2, 1, 3)에 `id 6, member_id 2`가 추가되면 `SELECT member_id, COUNT(*) FROM rental GROUP BY member_id;` 결과는?

| member_id | 내 답 | 정답 | 채점 |
|---|---|---|---|
| 1 | 3 | 3 | ✅ |
| 2 | 2 | 2 | ✅ 6번 카드가 2번 더미로 |
| 3 | 3 | **1** | ❌ 6번 카드는 3번 더미에 안 들어감 |

**문제**: rental(book_id: 1, 3, 1, 2, 1, 3)에서 책별 대여 횟수는?

**내 답**: `SELECT book.id COUNT(*) FROM rental GROUP BY book_id`

**결과**: `GROUP BY book_id`는 ✅. 고칠 곳 두 개.
- `book.id` → `book_id`: FROM에 rental만 꺼냈으니 book 표의 칸은 쓸 수 없다. rental 안의 `book_id`를 쓴다.
- 칸 사이 쉼표 빠짐.

```sql
SELECT book_id, COUNT(*) FROM rental GROUP BY book_id;   -- 1번 책 3, 2번 책 1, 3번 책 2
```

**SELECT 문법 점검 7문제**: 대화 중 퀴즈로 풀었다. 문제는 README의 "SELECT 뒤에 쓰는 규칙 5개"에 정리.

### 5-4 ~ 5-6단계

- **서브쿼리**: 두 번 설명을 들었지만 아직 이해하지 못했다. 과제 구현을 먼저 하고, 완성된 쿼리를 보면서 다시 검토하기로 했다.
- **UPDATE / DELETE**: FK 때문에 부모를 못 지우는 부분이 처음엔 이해되지 않았다. 부모와 자식을 **선으로 연결한 그림**("선이 붙어 있는 부모는 못 지운다")으로 이해했다.
- **인덱스**: 책의 찾아보기로 이해했다.

초안을 받고, 줄마다 "왜 이렇게 썼나"에 답하는 방식으로 검토했다.

### A. 스키마 (`sql/01_schema.sql`)

| 질문 | 내 답 | 정리 |
|---|---|---|
| CREATE TABLE만 하면 되지 DROP은 왜 필요한가? | (질문) | 두 번째 실행부터 `table already exists` 에러. 다시 실행할 수 있게 "있으면 지우고 새로". `IF EXISTS`는 처음 실행처럼 없을 때 넘어가게 함. `rm library.db`로 파일을 지우는 방법도 있지만 DROP 유지로 결정 |
| DROP은 왜 CREATE와 순서가 반대인가? | 카테고리를 지우면 book이 참조하는 카테고리 값이 의미 없는 데이터가 되기 때문 | ✅ FK가 막는다. 만들 땐 가리킬 대상이 먼저 있어야, 지울 땐 나를 가리키는 게 먼저 없어야 |
| `returned_at`에만 NOT NULL이 없는 이유는? | 처음엔 질문을 이해 못함 → 상황으로 다시 받고 "NOT NULL이면 에러 발생" | ✅ 빌리는 순간엔 반납일을 모름. NOT NULL이면 대여 기록 자체를 못 남김. NULL = 대여 중 (`WHERE returned_at IS NULL`) |
| `book.category_id`에 NOT NULL을 건 이유는? | 등록할 때 카테고리를 알 수 있지 않나? | ✅ 알 수 있으니 거는 게 맞음. **FK는 NULL을 막지 않으므로** FK + NOT NULL을 같이 걸어야 "모든 책은 반드시 카테고리에 속함" |
| `price`를 TEXT가 아니라 INTEGER로 한 이유는? | 글자로 정렬하면 숫자 정렬이 안 되고 아스키 기준 사전 순서로 정렬된다 | ✅ 실제로 `ORDER BY price DESC`에서 해리포터(15000)가 꼴찌, `WHERE price >= 10000`에 9000, 5000도 나옴. SUM은 맞게 나와서 더 알아채기 어려움 |

**배운 점**: NOT NULL은 "저장하는 순간 반드시 알 수 있는 값"에만 건다. FK와 NOT NULL은 검사하는 게 달라서 같이 걸어야 할 때가 있다.

### B. 샘플 데이터 (`sql/02_data.sql`)

**검토 질문**: 책이 없는 카테고리(시집, 요리)를 일부러 넣은 이유는? 이 데이터로 `category LEFT JOIN book`을 실행하면 몇 줄?

LEFT JOIN 처리 과정을 처음부터 다시 복습한 뒤 풀었다.

| 문제 | 내 답 | 정답 | 정리 |
|---|---|---|---|
| 전체 데이터 (카테고리 10, 책 12, 시집과 요리는 책 없음) | 카테고리가 10개니까 10줄 | **14줄** | ❌ 왼쪽 줄 수가 아니라 **짝 수만큼** 줄이 생김. 책 12권 → 12줄 + 짝 없는 카테고리 NULL 2줄 |
| 작게 다시: 카테고리 3 (소설, 만화, 시집), 책 3 (소설 2, 만화 1) | 소설-해리포터, 소설-어린왕자, 만화-원피스 | **4줄** | ❌ 시집-NULL이 빠짐. 내 답은 INNER JOIN의 정답 |
| 위에 요리(책 없음) 추가 | 위 3줄 + 시집-없음 + 요리-없음 | 5줄 | ✅ "없음"은 DB에서 NULL |
| 같은 데이터를 `JOIN`으로 | 3줄 | 3줄 | ✅ |

**배운 점**: LEFT JOIN 결과 줄 수 = **짝지어진 줄 수 + 짝 없는 왼쪽 줄 수**. 왼쪽 테이블 줄 수와 같다는 보장은 없다. 짝 있는 줄까지는 JOIN과 같고, LEFT JOIN은 짝 없는 왼쪽 줄을 NULL로 하나 더 붙인다.

**이 과정에서 정리한 것**

| 질문 | 정리 |
|---|---|
| `SELECT A, B, C` 뒤에 뭐가 오든 결과는 A, B, C 형태인가? | 맞다. **SELECT는 칸**을, FROM, JOIN, ON, WHERE는 **줄**을 정한다 |
| A, B, C는 FROM, JOIN 뒤에 있는 것이어야 하나? | `테이블.필드`에서 **테이블(점 앞)은 FROM, JOIN에 적힌 테이블**, **필드(점 뒤)는 그 테이블에 실제로 있는 칸**이어야 한다. 필드는 테이블이 아니라 테이블 안의 칸 |
| ON 뒤에는 무엇이 오나? | "**이 필드와 저 필드가 같으면 짝**"이라는 조건. 보통 자식 FK = 부모 PK. 잘못 쓰면 에러 없이 틀린 짝이 생김 |
| ON 안의 A = B와 B = A는 다른가? | 같다. 결과가 달라지는 건 LEFT JOIN에서 FROM과 JOIN에 둘 테이블을 바꿀 때뿐 |
| JOIN은 두 표를 새 사본으로 붙여 매칭한 뒤 보여주는 건가? | 맞다. 원본은 그대로, 짝지은 줄을 새 표에 붙이고, SELECT가 그중 칸을 고른다 |
| "결과 줄 수"는 무슨 뜻인가? | 결과 표의 데이터 줄(행) 개수. 헤더는 세지 않는다 |
| SQLite에서 NULL이 안 보이는데? | 터미널은 NULL을 빈칸으로 보여줌. `.nullvalue NULL`을 실행하면 NULL로 표시됨 |
| `rental.id`는 뭔가? | rental 테이블의 id 필드 = **대여 번호**. LEFT JOIN 결과에서 이 값이 NULL이면 "대여 기록이 붙지 않은 회원" |

**검토 질문 2**: 박민수, 한서윤을 rental에 일부러 넣지 않은 이유는?

```sql
SELECT member.name, rental.id
FROM member
LEFT JOIN rental ON rental.member_id = member.id
WHERE rental.id IS NULL;
```

| 문제 | 내 답 | 결과 |
|---|---|---|
| 결과는? | 박민수 NULL, 한서윤 NULL | ✅ |
| 모든 회원이 한 번 이상 빌렸다면? | (설명 들음) | **0줄**. NULL인 줄이 없어서 쿼리가 맞는지 결과로 확인할 수 없음 |

**배운 점**: 샘플 데이터에는 **쿼리에 걸리는 것과 안 걸리는 것이 둘 다** 있어야 쿼리가 제대로 동작하는지 결과로 보여줄 수 있다.

## 헷갈렸던 질문

| 질문 | 정리 |
|---|---|
| 엑셀과 DB를 가르는 기준은 PK 아닌가? 결국 키-밸류로 저장하는 것 아닌가? | 반만 맞음. 엑셀 행 번호는 위치, PK는 이름표라는 차이는 맞다. 하지만 PK는 엑셀로도 흉내 낼 수 있고, 핵심 차이는 **FK와 제약조건으로 규칙을 강제**하는 것. 키-밸류는 Redis 같은 다른 종류의 DB |
| `category (1) ──< book (N)` 표시는 뭔가? | 관계도 표기. `<`가 붙은 쪽이 여러 개(N) 쪽이고 FK를 가진 테이블 |
| 테이블이 4개인데 왜 줄은 3개인가? | 줄 하나는 **관계** 하나. 테이블 4개, 관계 3개 |
| NOT NULL이나 UNIQUE를 어기면 VALUES에서 거부하나? | INSERT **문 전체를 거부**하고 에러를 낸다. 에러 메시지에 어느 규칙, 어느 컬럼인지 나온다 |
| TEXT 칸에 숫자 2를 넣으면? | SQLite는 글자 `'2'`로 바꿔 저장한다. INTEGER 칸에 `'abc'`도 대부분 그냥 저장되니 주의 |
| SELECT가 맨 앞인데 어떻게 JOIN이 만든 표에서 칸을 고르나? | **쓰는 순서와 실행 순서가 다르다.** 실행은 FROM → JOIN → SELECT |
| `rental.id`, `member.name` 둘 다 rental의 데이터인가? | 아니다. 점 앞이 **출신 테이블** |
| `FROM rental`인데 rental에 없는 `member.name`을 어떻게 쓰나? | `FROM rental`만 있으면 에러. `FROM … JOIN … ON …`이 **한 덩어리로 재료 표**를 만들기 때문에 가능 |
| `;`까지가 최소 단위 오퍼레이션인가? | SQL은 `;`까지를 **한 문장**으로 끝까지 읽고 실행한다. "원자성"(한 줄 틀리면 전체 취소)과는 다른 이야기 |
| JOIN member는 member에 값을 붙이는 건가? | 원본은 안 바뀐다. 짝지은 결과를 **새 표에 나란히** 적는다. 또 member에는 `member_id` 칸이 없고 `id`만 있다 |
| 왜 JOIN에 member가 들어가나? ON만으로 안 되나? | FROM/JOIN은 **표를 꺼내는 것**, ON은 **짝 맞추는 규칙**. ON은 표를 꺼내 오지 않는다. rental은 이미 FROM으로 꺼냈으니 JOIN에는 아직 안 꺼낸 member를 쓴다 |
| FROM과 JOIN은 꺼내기만 하고 ON으로 병합되나? | 맞다. 다만 "병합"은 원본이 합쳐지는 느낌이라, "**조건에 맞는 줄끼리 이어 붙인 결과를 만든다**"가 정확 |
| 붙였을 때 실제로 남는 데이터는? | 줄은 **짝지어진 줄만**, 칸은 **두 표의 칸 전부**. 그중 SELECT에 적은 칸만 보여준다 |
| ON 안의 왼쪽, 오른쪽을 바꾸면 값이 달라지나? | 안 달라진다. LEFT JOIN의 "왼쪽"은 `=`의 왼쪽이 아니라 **FROM에 쓴 표** |
| "회원 이름과 대여 번호" 순서라서 `FROM member`인가? | 아니다. INNER JOIN은 순서 무관. LEFT JOIN일 때만 순서가 중요하고, 기준은 단어 순서가 아니라 **"누구를 전부 남길지"** |
| COUNT는 칼럼 기준에 따라 옆에 총 토탈을 보여주는 건가? | 거의 맞다. 기준은 **GROUP BY에 적은 칸**이 정하고, 옆의 숫자는 전체 합계가 아니라 **그 값에 해당하는 줄 수**(더미별 개수) |
| 자식이 있는 부모는 왜 못 지우나? | 지우면 자식이 **없는 번호를 가리키게** 된다. INSERT 때 없는 번호를 막은 것과 같은 규칙. 지울 때는 자식 먼저 |
| 인덱스는 뭔가? | 책 맨 뒤의 **찾아보기**. 결과는 같고 찾는 속도만 빨라진다. WHERE, JOIN에 자주 쓰는 칸에 건다 |
