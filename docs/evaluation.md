## 항목 2. 설계를 설명할 수 있는가

> 각 질문마다 **보여줄 곳**과 **말하기** 예시입니다. 말하기는 외우지 말고 흐름만 잡아 본인 말로 합니다.

### 테이블을 왜 이렇게 나눴고, 각 테이블의 역할은?

**보여줄 곳**: [README 스키마 그림](../README.md#테이블-구조-스키마)

| 테이블 | 역할 | 한 줄 = |
|---|---|---|
| category | 책 분류 | 카테고리 하나 |
| member | 회원 정보 | 회원 한 명 |
| book | 책 정보 | 책 한 권 |
| rental | 누가 어떤 책을 언제 빌렸나 | **대여 한 건** (사건) |

**말하기**
> "엑셀 한 장에 적으면 김철수가 4번 빌릴 때 이름, 이메일, 전화번호를 4번 적어야 합니다. 그래서 **바뀌지 않는 정보**(회원, 책, 분류)와 **일어난 일**(대여)을 나누고 번호로 연결했습니다."

**꼬리질문 "rental은 왜 따로?"** → "book에 회원 칸을 두면 책 한 권에 한 명밖에 못 적습니다. 같은 책을 여러 번 빌리니까 대여를 따로 기록했습니다."

### 1:N 관계가 실제로 어떤 의미인가?

**보여줄 곳**: [Q07 스크린샷](../results/images/q07.png) (김철수 줄이 4개)

| 관계 | 실제 의미 | 데이터 예시 |
|---|---|---|
| category 1 : N book | 카테고리 하나에 책 여러 권 | 소설 → 해리포터 2권, 어린왕자 |
| member 1 : N rental | 회원 한 명이 여러 번 빌림 | 김철수 → 대여 1, 3, 6, 12번 (4회) |
| book 1 : N rental | 책 한 권이 여러 번 대여됨 | 해리포터와 마법사의 돌 → 대여 1, 4, 7, 12번 (4회) |

**말하기**
> "회원 한 명이 여러 번 빌리니까 member와 rental은 1:N입니다. 김철수는 member에 1줄인데, rental에는 `member_id = 1`인 줄이 4개(1, 3, 6, 12번) 있습니다. FK는 항상 여러 개인 N 쪽에 둡니다 (`book.category_id`, `rental.member_id`, `rental.book_id`)."

### 컬럼 타입은 왜 그렇게 골랐나?

| 칸 | 타입 | 이유 |
|---|---|---|
| id, `*_id` | INTEGER | 번호. FK로 같은 번호끼리 비교 |
| name, title, email, phone | TEXT | 글자. 전화번호는 계산하지 않고 앞의 0을 지키려고 TEXT |
| price | INTEGER | 글자로 저장하면 정렬과 비교가 **사전 순서로 조용히 틀림** ('9000'이 '15000'보다 위). SUM, AVG에도 사용 |
| rented_at, returned_at | DATE | 날짜라는 뜻을 드러내려고 DATE로 적음. **SQLite에는 날짜 타입이 따로 없어** 실제로는 `'YYYY-MM-DD'` 글자로 저장됨. 0을 채우고 큰 단위가 앞이라 글자 순서 = 날짜 순서여서 정렬, 비교가 맞게 됨 |

### 인덱스는 어디에 걸었고 왜 그 칸인가?

**보여줄 곳**: [Q15 스크린샷](../results/images/q15.png) (`idx_rental_member_id`)

**말하기**
> "`rental.member_id`에 걸었습니다. Q07, Q12처럼 '이 회원의 대여 기록'을 찾는 일이 많은데, 인덱스가 없으면 rental을 처음부터 끝까지 봐야 합니다. 인덱스는 책 뒤의 찾아보기처럼 바로 찾게 해 주고, **결과는 그대로, 속도만** 바뀝니다."

**꼬리질문 "정말 빨라졌는지 어떻게 아나?"** → "`EXPLAIN QUERY PLAN SELECT * FROM rental WHERE member_id = 1;`로 물어보면, 인덱스 전에는 `SCAN rental`(전부 훑기), Q15 후에는 `SEARCH rental USING INDEX idx_rental_member_id`(찾아보기 사용)로 바뀝니다." ([개념 6](concepts.md#6-인덱스는-왜-필요하고-어디에-거나))

**꼬리질문 "모든 칸에 걸면?"** → "넣고 고칠 때마다 인덱스도 고쳐야 해서 INSERT, UPDATE가 느려집니다. 자주 찾는 칸에만 겁니다. `id`는 PK라 이미 자동으로 인덱스가 있습니다."

**보여줄 곳**: [README 스키마 그림](../README.md#테이블-구조-스키마)의 member ↔ rental 선

**말하기**
> "PK는 **내 번호**입니다. `member.id`가 회원 한 명을 가리키고, 겹치거나 비어 있을 수 없습니다. FK는 **남의 번호를 적어 둔 것**입니다. `rental.member_id`에 member의 id를 적어서 이 대여가 누구 것인지 연결합니다. 김철수(id 1) 한 명에 rental 4줄이 1을 적고 있어서 1:N입니다."

### INNER JOIN과 LEFT JOIN 차이를 결과로

**보여줄 곳**: [Q06 스크린샷](../results/images/q06.png)과 [Q08 스크린샷](../results/images/q08.png)을 나란히

**말하기**
> "두 쿼리는 `LEFT` 한 단어만 다릅니다. Q06(JOIN)은 12줄로 책이 있는 분류만 나옵니다. Q08(LEFT JOIN)은 14줄이고, 책이 없는 **시집, 요리**도 나오는데 제목이 NULL입니다. LEFT JOIN은 **FROM에 쓴 표(category)의 줄을 모두 남기고**, 짝이 없으면 NULL로 채웁니다."

## 항목 4. 경험을 말할 수 있는가

### 가장 복잡했던 쿼리와 푸는 과정

**보여줄 곳**: [Q11 스크린샷](../results/images/q11.png)

**Q11 가장 많이 대여된 책 TOP 3**입니다. 결과: 해리포터와 마법사의 돌 4회, 해리포터와 비밀의 방 2회, 원피스 1권 2회.

```sql
SELECT book.title, COUNT(*)
FROM rental
JOIN book ON rental.book_id = book.id
GROUP BY book.title
ORDER BY COUNT(*) DESC
LIMIT 3;
```

**말하기**: 쓴 순서가 아니라 **실행 순서**로 설명합니다.
1. `FROM rental JOIN book ON ...` → 대여 기록 15줄마다 책 제목을 붙인 표를 만든다
2. `GROUP BY book.title` → 제목이 같은 줄끼리 더미를 나눈다
3. `COUNT(*)` → 더미마다 줄을 센다 = 대여 횟수
4. `ORDER BY COUNT(*) DESC` → 많은 순으로 정렬
5. `LIMIT 3` → 위에서 3개만

2위가 2회로 동점(해리포터와 비밀의 방, 원피스 1권)이라, 동점끼리의 순서는 SQL이 정해 주지 않습니다. 순서까지 정하려면 `ORDER BY`에 기준을 더 적어야 합니다.

**꼬리질문 "제목이 같은 책이 있으면?"** → "두 책이 한 더미로 합쳐져서 틀린 결과가 됩니다. 이번 데이터에는 같은 제목(같은 이름의 회원)이 없어서 문제없지만, 정확히 하려면 PK인 `book.id`로 묶어야 합니다. Q09의 `GROUP BY member.name`도 같습니다."

**꼬리질문 "서브쿼리(Q12)는?"** ([Q12 스크린샷](../results/images/q12.png)) → "괄호 안 `SELECT member_id FROM rental`로 **빌린 적 있는 회원 번호 목록**을 먼저 만들고, 바깥에서 그 목록에 **없는**(`NOT IN`) 회원만 고릅니다. 결과는 박민수, 한서윤입니다."

### 가장 어려웠던 부분과 해결 방법

> [연습 기록](practice.md)에 남긴 실제 오답과 질문을 바탕으로 정리했습니다. **본인 경험이라 하나를 골라 직접 말합니다.** "막힌 것 → 어떻게 풀었나 → 지금은 이렇게 이해한다" 순서로 말하면 됩니다.

| 어려웠던 것 | 막힌 지점 | 해결한 방법 |
|---|---|---|
| JOIN | SELECT가 맨 앞인데 어떻게 JOIN 결과에서 칸을 고르는지, `FROM rental`인데 `member.name`을 어떻게 쓰는지 | **쓰는 순서와 실행 순서가 다르다**는 걸 알고, FROM과 JOIN이 함께 "재료 표"를 만든다는 그림으로 이해 |
| LEFT JOIN 방향 | "LEFT JOIN이면 짝 없는 건 다 남는다"고 생각해서 오답 | "**FROM에 쓴 표만** 전부 남는다"를 왼쪽, 오른쪽을 바꾼 두 그림으로 비교 |
| GROUP BY | COUNT, SUM, AVG를 한 번에 배울 때 이해 못함 | COUNT 하나만, **카드를 더미로 나눠 세는** 그림으로 다시 배움 |
| FK와 DELETE | 왜 부모를 못 지우는지 | 부모와 자식을 **선으로 연결한 그림**("선이 붙은 부모는 못 지운다") |
| 서브쿼리 | 두 번 설명을 들어도 이해가 안 됨 | 구현을 먼저 마치고, 완성된 Q12를 "사람이라면 어떻게 찾나"(① 빌린 사람 번호 적기 ② 명단에서 없는 사람 고르기)로 바꿔 봄. 같은 모양의 "안 빌린 책" 문제를 직접 풀어 정답 |

**말하기 예시 (LEFT JOIN을 고른 경우)**
> "LEFT JOIN이 가장 어려웠습니다. 처음엔 '짝이 없는 건 양쪽 다 남는다'고 생각해서 틀렸습니다. 왼쪽과 오른쪽 표를 바꾼 그림 두 개를 비교해 보고 **FROM에 쓴 표만 전부 남는다**는 걸 이해했습니다. 그래서 Q06과 Q08을 LEFT 한 단어만 다르게 만들어 결과로 확인했습니다."
